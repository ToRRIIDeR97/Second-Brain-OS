# Performance and security audit — 7 September 2026

The audit found one critical content-execution vulnerability and several missing privilege boundaries. The findings below are retained as the original evidence record; all eight were remediated in the working tree on 7 September 2026.

Scope: the active Electron product in `opencode/`, including its preload bridge, local server, Second Brain notes/projects, Google planner integration, and Markdown rendering. The legacy Tauri donor app, hosted console, and unrelated upstream packages were not comprehensively audited. Reviewed commit: `de1ac5adb00146e625010719005c9ba736da1a6e`. This is a source audit with isolated runtime checks, not a penetration-test certification or a production performance profile.

| S4  | High     | Workspace plugins execute without a workspace trust gate     | Fixed with safe desktop default                    |
| S5  | High     | Google event restrictions trust renderer-supplied metadata   | Fixed                                              |

| P2  | High     | Note listings read entire files without read-size limits     | Fixed with bounded reads and local summary updates |

**S1 — Markdown frontmatter executes code.** [Notes decode](../../opencode/packages/opencode/src/knowledge/note.ts#L153), [project decode](../../opencode/packages/opencode/src/project/brain.ts#L194), and [configuration parsing](../../opencode/packages/core/src/config/markdown.ts#L3) pass workspace text to `gray-matter` without restricting its engines. The installed 4.0.3 implementation accepts `---javascript` and evaluates the frontmatter. The built local-server bundle also contains that engine. Loading the Notes or Projects listing reaches these parsers; the attacker needs a file in the opened workspace, not server credentials. Execution occurs before metadata validation and has the server process's privileges. The isolated check set an in-memory marker; it executed no command and accessed no secrets. `matter.stringify(body, data)` also parses string bodies, so writes need the same treatment. Use a data-only frontmatter parser, explicitly reject executable language selectors, and cover all read/write/config callers with regression checks.

**S2 — Storage IPC allows path traversal and private-store access.** [Storage handlers](../../opencode/packages/desktop/src/main/ipc.ts#L128) pass renderer-controlled store names to [getStore](../../opencode/packages/desktop/src/main/store.ts#L15). `electron-store` forwards the name to `conf`, which resolves it against `userData`; absolute names and `../` are not confined. With temporary test files, `../outside.json` successfully read and modified JSON outside the synthetic data directory. This exposes JSON readable by the application user and allows JSON creation/modification; it is not a demonstrated arbitrary-binary-file read. A compromised renderer can also address native-only stores such as `second-brain.google`. Encryption of Google tokens does not protect the surrounding authorization/outbox state from these generic operations. Introduce an explicit renderer store allowlist, deny private namespaces, validate main-frame sender/origin, and enforce path containment including symlinks. Test rejection through the IPC boundary.

**S3 — Renderer-selected executable launch bypasses the sandbox.** [open-path handler](../../opencode/packages/desktop/src/main/ipc.ts#L233) accepts both `path` and `app` from the [preload API](../../opencode/packages/desktop/src/preload/index.ts#L118). On Windows/Linux, it calls `execFile(app, [path])`; on macOS it launches the supplied application using `open -a`. There is no application allowlist, workspace/picker authorization, or sender validation in this handler. A compromised renderer can choose an interpreter and an attacker-controlled script on Windows/Linux; macOS still exposes unrestricted application launching. This is a privilege-escalation path contingent on renderer execution, not an independently demonstrated XSS. Accept a fixed application identifier resolved in the main process and a validated workspace resource or picker token. Do not accept executable paths from the renderer.

**S4 — Opening a workspace can load its code before trust approval.** [Config discovery](../../opencode/packages/opencode/src/config/config.ts#L405) loads project configuration and discovers `.opencode/plugin(s)/*.{ts,js}`. [Bootstrap](../../opencode/packages/opencode/src/project/bootstrap.ts#L33) initializes plugins, and the [loader](../../opencode/packages/opencode/src/plugin/loader.ts#L136) dynamically imports them. The traced path has no per-workspace trust decision; `pure` and project-config environment flags are global opt-outs. Imported module top-level code executes before any agent tool approval could help. This inherited OpenCode behavior conflicts with Second Brain's requirement to treat workspace content as data unless explicitly trusted. Gate local plugin loading, dependency setup, and other executable project configuration behind persisted workspace trust. The current [threat model](../security/threat-model.md#L3) still describes a Rust/Tauri boundary and cannot serve as evidence that the Electron product enforces it.

**S5 — Calendar write restrictions rely on attacker-controlled facts.** [googleEventPayload](../../opencode/packages/desktop/src/main/google-calendar-domain.ts#L70) blocks participant-facing/recurring changes using `participantCount` and `recurringSeriesId` supplied by the renderer. [IPC](../../opencode/packages/desktop/src/main/ipc.ts#L108) forwards the input, and [dispatch](../../opencode/packages/desktop/src/main/google-calendar.ts#L394) updates/deletes the supplied provider ID without fetching authoritative event metadata. A connected account with write consent is required. The actual domain function rejected an event with two participants but accepted the same event after setting the count to zero. Google PATCH preserves omitted fields, so omitting attendees does not turn an existing meeting into a private event. [Google API semantics](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch). Retrieve and validate current provider metadata in the main process, bind the decision to the event ID/version, and revalidate durable retries. No live Google mutation was performed.

**P1 — Every distinct parsed document remains in memory.** The same unconfigured `matter(source)` calls in S1 enable `gray-matter`'s process-global cache keyed by the entire input. The installed implementation has no eviction, and no application caller clears or bounds it. Reading different notes and saving new versions accumulates complete content for the server lifetime, even after leaving a workspace. A fresh Node 24 process parsed 100 distinct approximately 512 KiB documents: after forced garbage collection, heap usage grew about 50 MiB and RSS about 98–105 MiB across two runs; all 100 cache entries remained. This measures parser retention, not application latency or Electron RSS. Replace the parser as part of S1, or disable its implicit cache and use only a bounded cache if measurements justify one. Verify repeated edits reach a memory plateau.

**P2 — Lists perform full-content reads with no input byte budget.** [KnowledgeNote.list](../../opencode/packages/opencode/src/knowledge/note.ts#L62) first collects all matching paths, then reads/parses/hashes up to 500 complete files with concurrency eight. [readCard](../../opencode/packages/opencode/src/knowledge/note.ts#L136) has no size check; the 5 MiB guard applies only to API writes. Externally added files can be much larger. Even 500 notes at the permitted write size represent about 2.44 GiB of input for one listing, with cache retention compounding the cost. [Saving a note](../../opencode/packages/app/src/pages/notes.tsx#L232) refetches the entire list. Project lists similarly read up to 1,000 complete cards, and every project update calls that listing. Enforce bounded reads and total request budgets; update the saved note's summary locally and maintain rebuildable summaries keyed by file change. Apply traversal limits during enumeration and expose pagination rather than silently truncating before sorting. No large-workspace UI timing was measured.

**P3 — Serialized retries delay every other Google operation.** [sync](../../opencode/packages/desktop/src/main/google-calendar.ts#L130) holds a global `busy` flag while draining calendar and task outboxes before fetching results. Every [dispatch](../../opencode/packages/desktop/src/main/google-calendar.ts#L394) refreshes the access token independently; requests have 30-second timeouts, and retry loops have no overall deadline, cancellation, or backoff. Twenty queued operations whose token requests each time out can consume roughly ten minutes before the normal sync fetch starts. That is a calculated failure scenario, not observed network timing. During that time writes and disconnect fail as busy. Reuse an access token for the batch, stop or defer retries after connectivity/authentication failures, and bound/cancel a sync run. Keep per-operation retry and idempotency guarantees.

Existing protections worth preserving: Electron enables context isolation, disables renderer Node integration, and enables its sandbox; navigation and external URL schemes are restricted; the managed server binds loopback with a generated password; note paths are canonicalized with symlink-escape checks; picked attachments have sender-bound tokens and size budgets; Markdown HTML is sanitized; Google OAuth uses PKCE/state and OS-backed encryption; file updates compare expected bytes under a process-local lock.

Additional hardening: the packaged renderer has no Content Security Policy, and `windows.ts` overwrites response CORS headers with wildcards across the Electron session. Add a restrictive renderer CSP and scope any necessary CORS adjustment to explicit application endpoints. These are defense-in-depth concerns; this review did not establish a Markdown XSS or an unauthenticated remote server compromise. Electron recommends restrictive CSP and validating all IPC senders. [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).

Validation and limits: the remediation checks now verify rejection of executable frontmatter without parser-cache retention, store/application allowlists, and provider-derived participant policy. Desktop, core, and server TypeScript checks pass. Bun is absent from this environment, so Bun unit tests and the complete build were not run. The linter could not load the repository configuration because the installed oxlint rejects `options.typeAware` outside its root configuration. No running app/server was restarted and no real provider account was modified. No complete dependency-advisory scan, installer/signing review, browser exploit test, or production CPU/startup/frame-time profile was performed. Re-run the checks with [audit checks](2026-09-07-checks.mjs).

The remaining validation work is to run Bun tests/build when Bun is available, then record cold/warm Notes/Projects load times and planner behavior under offline or slow-provider conditions using representative workspaces.
