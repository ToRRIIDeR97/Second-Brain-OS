# Architecture views (UML)

This is the master graph document for the active Electron/OpenCode app. The
[architecture overview](README.md) explains component boundaries in prose,
and the [threat model](../security/threat-model.md) owns trust boundaries.
This document holds the detailed views.

Conventions:

- Notation follows [UML 2.5.1](https://www.omg.org/spec/UML/2.5.1). Each family
  appears in a fixed order: structural (component, deployment, class), then
  behavioral (activity, state machine), then interaction (sequence).
- Source paths are relative to `opencode/packages/` unless a diagram says
  otherwise.
- Solid arrows are calls or data flow, and dashed arrows are replies or
  optional paths. Red boxes mark known gaps or relationships that haven't been
  verified at runtime.
- The SVGs in [`docs/diagrams/`](../diagrams/) are generated by the Python
  scripts in [`docs/diagrams/generate/`](../diagrams/generate/). Edit a script
  and run the command in its header, or edit the SVG directly.

The views were mapped from source on 2026-10-05. They are a source-level
reading of the code, not a runtime trace, except where a step says it was run.

### Deployment

![Deployment view: Electron main, renderer and utility-process server on the user machine, optional harness processes and CLI daemon, profile and workspace stores, Google, LLM providers and the build host](../diagrams/deployment.svg)

- The server runs in an Electron `utilityProcess` on `127.0.0.1` at an
  ephemeral port. Its password is a UUID generated at each launch
  (`desktop/src/main/index.ts`, `server.ts`).
- `userData` is `appData/<appId>`. The server sets `XDG_STATE_HOME` to
  `userData` by default, but `auth.json` and `opencode.db` live in the XDG
  data directory (`core/src/global.ts`, `core/src/database/database.ts`,
  `opencode/src/auth/index.ts`).
- Those XDG directories are named `tenon-workbench`, separate from upstream
  OpenCode's `opencode` folders. `core/src/legacy-storage.ts` copies the
  legacy `opencode` data, config and state folders once on first start; see
  [Harness drivers and registration](README.md#harness-drivers-and-registration).
  The Electron app ID is `io.github.torriider97.tenonworkbench[.dev|.beta]`, so
  `userData` no longer collides with upstream OpenCode Desktop. On the dev
  channel, `desktop/src/main/user-data-migration.ts` copies the old
  `ai.opencode.desktop.dev` `userData` once before startup sets the path.
- The `opencode-cli` daemon (`OPENCODE_SIDECAR_V2=1`) ships only in the
  development channel. Packaging and update limits are covered in
  [release operations](../release-operations.md).

### Class

![Class view: Project, Session, SessionMessage, SessionInput, durable Event, permission types and HarnessInstance; Location, BrainProject, KnowledgeNote, CalendarSnapshot, CalendarEvent and Task](../diagrams/class-domain.svg)

Notes on the class view:

- A session's harness binding (instance, model and revision) and its
  per-instance continuations (`harnessContinuations[instanceID]` =
  `{ nativeID, lastSeenMessageID }`) live in the session's `metadata` JSON.
  They have no separate table.
- Built-in `HarnessInstance` IDs are `opencode` (driver `opencode`, shown as
  Tenon Workbench), `codex`, `opencode-acp` (driver `acp`, shown as OpenCode) and
  `claude-code` (driver `acp`, shown as Claude Code).
  They are reserved, so `harnesses.json` and config files can't replace them.
- Permission requests exist only in memory. Saved permission rows are allow
  rules, scoped to a project. Values saved from a command or path are literal
  patterns (`[*]` and `[?]` stand for a literal `*` and `?`).
- `BrainProject` and `KnowledgeNote` are Markdown files. `CalendarSnapshot` is
  one JSON file per location. None of them is stored in SQLite. A note is
  deleted only with the revision the caller read; writes refuse a file that
  would exceed the read limit.
- `BrainProject.location.path` names the Project's folder (inside the
  workspace's `projects` folder, or an absolute linked folder). A legacy
  `location.workspaceId` is an OpenCode `Project.id`. A BrainProject's thread
  directory is its folder, else that Project's worktree, else its card folder
  `.tenon/projects/<id>/`. Sessions belong to it by the folder holding their
  `directory`, not by a stored foreign key.
- `WorkspaceManifest` (`.tenon/workspace.json`, linked folders) marks a
  workspace root. The linked-folder index (`workspace-links.json` in the data
  folder) maps linked folders back to their workspace; a scan rebuilds it.

## Behavioral views

### Activity: prompt run

![Activity: prompt admission, coordinator wake, input promotion, harness streaming, local tool permission checks, step completion or failure, and interrupt](../diagrams/activity-prompt-run.svg)

Runtime notes:

- Tools run by Codex or ACP agents are provider-executed. The runner only
  records them, and their approvals arrive through the harness permission
  bridge.
- A provider-executed subagent can report progress while it runs. A
  `tool-progress` stream event becomes `session.next.tool.progress`, which
  replaces the running tool's `structured` checkpoint.
- If the user declines a local tool, the drain stops. A declined ACP
  permission instead sends a reject option back to the agent.

### Activity: Second Brain write

![Activity: authorization, workspace routing, decode, path containment, create or compare-and-swap update, and best-effort timeline sync, with 400, 401, 409 and 500 exits](../diagrams/activity-second-brain-write.svg)

Some details of the write path:

- A calendar write replaces the whole `{events, tasks}` document; there is no
  per-task endpoint.
- Notes, projects and the calendar use different revisions:
  - notes: a SHA-256 hash of the file;
  - projects: `updatedAt`;
  - calendar: a ULID.
- No delete endpoints exist for notes, projects or tasks.
- One handler mapper turns failures into HTTP errors: a domain or path
  rejection is a 400 `SecondBrainInvalidError` whose `data.message` is the
  reason, a missing record is 404, a stale write is 409, and IO or permission
  failures are a logged 500. Logs carry the error tag, reason and relative
  path, never content.
- When a request's workspace folder (`directory`, `location[directory]` or
  `x-opencode-directory`) no longer exists, the server-wide error middleware
  turns the resulting defect into a 404 `WorkspaceFolderNotFoundError` instead
  of a 500. Other unexpected defects stay a logged 500 with an `err_` ref.
- `FileMutation` replaces a file through a synced sibling temp file and a
  rename, keeping the old permission bits. It refuses a target that isn't
  writable, and writes in place when the directory refuses new files. A
  calendar file that isn't JSON or isn't a calendar document is moved aside to
  `calendar-v1.json.corrupt-<time>` on the next save; one that only fails
  validation still fails the save.
- Calendar saves (with their timeline sync), Project create and update, and the
  Workspace migration share one lock per Brain directory. The timeline sync
  rewrites only `projects/<id>/timeline/calendar.json` files whose items
  changed; no code reads those files yet.
- Note and Project listings skip an unreadable or malformed file with a
  warning. Project cards are read only from `projects/project_*.md` and
  `projects/project_*/project.md`; a managed card wins over a flat card with
  the same id, and a card whose id differs from its path is ignored.

### Sequence: ACP harness turn

![Sequence: prompt admission, drain, ACP runtime open with session load or new, streaming updates, permission ask answered in the renderer, completion and interrupt](../diagrams/sequence-acp-turn.svg)

The built-in `opencode-acp` instance (upstream OpenCode started as
`opencode acp`) and `claude-code` instance (`claude-agent-acp`) follow this
sequence unchanged. The Codex driver follows the
same outline. It speaks the `codex app-server`
JSON-RPC protocol (`thread/start` or `thread/resume`, `turn/start`,
`turn/interrupt`) instead of ACP. Its approvals come from
`item/*/requestApproval` requests.

Before `session/prompt` (not drawn in the diagram), the ACP driver switches the
model and then the reasoning effort (`thought_level` option) when they differ
from the session's, through `session/set_model` or `session/set_config_option`.
For older OpenCode, which lists levels as `<base>/<level>` models, the chosen
level is sent as a switch to that model instead.

Handoff text in the first prompt of a runtime (not drawn in the diagram):

1. Read `harnessContinuations[instanceID]`. If there is no entry, open a new
   thread or session.
2. If the resume succeeded and the entry has a `lastSeenMessageID`, send the
   messages after it inside `<handoff-history>`, then the user message. If
   nothing new happened, send only the user message.
3. If the resume failed, or the thread is new, send the bounded full history
   inside `<handoff-history>`, then the user message.
4. When a turn ends without an error, publish `HarnessContinuationSet` with the
   answered user message as `lastSeenMessageID`.

The first prompt of a runtime also starts with a `<tenon-context>` block:
workspace and Project folders, the AGENTS.md text in effect (one
`<agents-md>` element per file) and the abilities guidance, which names
`ask_user` only when the `tenon` server is attached (`renderHarnessPrompt`,
`core/src/tenon-context.ts`). Later turns in the same runtime send only the user message. See
[Harness handoff](README.md#harness-handoff) for the budget and wrapper.

### Sequence: cross-harness delegation

![Sequence: the harness runtime gets a scoped token for the loopback MCP endpoint, the calling agent invokes delegate_task, the server creates a child Run on the target harness, waits for its drain and returns the child's final reply](../diagrams/sequence-delegation.svg)

The built-in loop skips the MCP hop: its `delegate_task` tool calls the same
task handler directly. The same endpoint serves `ask_user` (not drawn): the call
becomes a `QuestionV2` request in the caller's session, answered in the
question dock; see [Questions from harnesses](README.md#questions-from-harnesses). See [Cross-harness delegation](README.md#cross-harness-delegation).

## Unverified relationships and assumptions

The following were inferred from source and haven't been confirmed at runtime.

- **Second Brain middleware order.** The middleware order for Second Brain
  routes (authorization outermost) was inferred from Effect layer types.
- **Process-local write lock.** File compare-and-swap uses a process-local
  mutex. A second process writing the same workspace isn't excluded, but
  writes go through a synced temp file and a rename, so a crash can't
  truncate a file.
- **Harness skill folders.** The folder lists in `core/src/harness/skills.ts`
  were checked against the Codex, OpenCode and Claude Code docs on
  2026-10-22. They will drift if those tools change their conventions.
- **Per-subagent usage.** Whether an ACP agent sends `usage_update` for a
  child session at all is up to the agent. Upstream OpenCode's behavior wasn't
  confirmed; the agent tab shows "Not reported" when it doesn't.
- **v2 CLI daemon.** The opt-in v2 sidecar is upstream's `opencode-cli`
  background service. It is allowed only on the development channel, the
  only one that bundles the CLI, and it outlives the app by design
  (`opencode-cli service stop` ends it).
- **Server health checks.** A server that exits after ready is restarted on
  the same port and password with backoff
  (`desktop/src/main/sidecar-supervisor.ts`); the renderer's status popover
  polls server health. If the first start fails because another process took
  the picked port, a new port is picked (up to three tries).

## Not drawn

- Renderer internals (providers, query caches, stores) are summarized in the
  component table instead of drawn. They change often and have no trust
  boundary.
- The legacy V1 session runtime in `opencode/src/session/` is still mounted
  for legacy routes but isn't used by Harness runs. It's left out to keep the
  views readable.
- WSL sidecars appear only in the deployment view. Their internals weren't
  mapped.
